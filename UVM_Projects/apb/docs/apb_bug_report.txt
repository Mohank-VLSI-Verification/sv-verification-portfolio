# APB UVM Verification — Bug Report v1.0

## 1. Scope

End-to-end verification of an APB3-style slave with a 32x32 memory array, exercising:
- Valid-range writes/reads (PADDR 0–31)
- Out-of-range error responses (PADDR > 31, PSLVERR = 1)
- Reset behavior
- Protocol-handshake invariants via 5 SVA assertions
- Functional coverage closure via uvm_subscriber-based collector

DUT: `apb_ram` (4-state FSM: idle → setup → access → transfer)
Reference model: `ref_model` (32-entry mirror array with PSLVERR prediction logic)

## 4. Bugs Found and Fixed (Testbench)

### Bug TB-1 — Sibling Constraint Conflict

**Symptom:** "Valid-only" sequences (write_data, read_data, etc.) were producing PADDR values like `1111385171`, `2138514015` — far outside the constrained `[0:31]` range.

**Root cause:** Transaction class declared two sibling constraints:
```
constraint addr_c     { PADDR <= 31; }
constraint addr_c_err { PADDR > 31; }
```
Sequences used `addr_c.constraint_mode(0/1)` to toggle them. In Vivado XSIM, the toggle behavior was unreliable — `assert(tr.randomize)` was silently failing on contradiction, and PADDR retained leftover bits.

**Fix:** Collapsed both constraints into a single conditional, gated by a class member knob:
```
bit valid_addr = 1'b1;
constraint addr_c {
  if (valid_addr) PADDR inside {[0:31]};
  else            PADDR inside {[32:32'hFFFF_FFFF]};
}
```
Each sequence now sets `tr.valid_addr` before `randomize()`, and `randomize()` return value is checked with `uvm_error` on failure.

---

### Bug TB-2 — Monitor Sampling Race

**Symptom:** Monitor reported `slverr=0` for error-range transactions where reference model correctly predicted `slverr=1`. Symptom appeared as PSLVERR mismatches in scoreboard, falsely flagging the DUT.

**Root cause:** Monitor sampled at `@(negedge vif.pready)` — but PSLVERR is updated by the DUT on the same clock that drives PREADY high. At negedge of PREADY, the PSLVERR value was already transitioning back to 0 (idle state), causing a one-cycle stale read.

**Fix:** Replaced edge-based sampling with a posedge-clock guarded check:
```
@(posedge vif.pclk);
if (vif.presetn && vif.psel && vif.penable && vif.pready) begin
  // sample here — DUT signals are stable in this cycle
end
```
Same fix applied to reference model so both samplers fire at the same clock instant — no race between them.

**Verification:** Re-run showed monitor and reference model agreeing on PSLVERR for every transaction. All MISCMP entries eliminated.

---

### Bug TB-3 — uvm_sequence_library Runtime Null Deref

**Symptom:** `uvm_sequence_library::execute()` threw "Accessing non-static members of a null object" at line 25850 of `xlnx_uvm_package.sv`, despite all 7 sequences being correctly added via `add_typewide_sequence()` in the library constructor.

**Root cause:** Vivado XSIM 2025.2's UVM 1.2 implementation of `uvm_sequence_library::execute()` does not reliably resolve typewide-registered sequence handles at runtime — `create_seq_by_typename` returns null.

**Fix:** Dropped the `uvm_sequence_library` pattern entirely for this project. Test class now instantiates and starts each of the 7 sequences sequentially in `run_phase`. This guarantees full coverage path traversal (every sequence executed) at the cost of randomized selection.

**Verification:** Re-run cleanly executed all 7 sequences without exception. `uvm_sequence_library` is not referenced in the locked TB.

## 6. Coverage Analysis — 80.95%

Three crosses defined:

| Cross | Status |
|-------|--------|
| `op_x_paddr` (read/write × {addr_zero, valid_lo, valid_mid, valid_hi, addr_max, error_range}) | Hit on all six address buckets for both read and write |
| `op_x_pslverr` (read/write × {no_err, err}) | All four bins hit |
| `paddr_x_pslverr` (addr buckets × {no_err, err}) | Partial — valid_*×no_err hit, error_range×err hit; valid_*×err and error_range×no_err are by-design empty |

`pwdata_cp` crosses on write-side likely account for the remaining 19.05% gap. To be revisited in v2.

**Coverage holes are mostly impossible-by-design crosses** (e.g. valid PADDR cannot produce PSLVERR=1), not stimulus gaps. Confirmed by manual inspection of `cov_report/functionalCoverageReport/dashboard.html`.
